# 配图质量：测量口径与结论

## 为什么要专门写口径
第 34 轮我测出 "PSNR 7–15dB"（灾难级），第 35 轮又测出 "23–26dB"，
两次都与我长期声称的 "37–41dB" 矛盾 —— 三次结论三个样。
根因是**测量口径不一致**，不是图片有问题。

## 正确的口径
**在变体自身的显示尺寸上比对。**

做法：把原图也缩放到该变体尺寸（作为基准），再与变体比 PSNR。

错误做法（我踩过）：
- 直接把 400px 变体与 1600px 原图比 → ImageMagick 会按尺寸不匹配处理，结果无意义（7–15dB）
- 把变体**放大回 1600** 再与原图比 → 测的是"放大插值的损失"，不是用户实际观感（23–26dB）

## 实测结果（同尺寸口径）

| 图片 | 400px（1x 手机） | 800px（2x 手机/1x 平板） | 1200px（2x 桌面） |
|---|---|---|---|
| kongming-architecture | 36.5 dB | 37.8 dB | 37.7 dB |
| xingju-cyberpunk | 35.0 dB | 36.7 dB | 36.8 dB |
| zen-workflow | 37.6 dB | 38.5 dB | 38.6 dB |

**全部落在 35.0–38.6 dB，属"良好"档**（参考：>40 优秀 / 35–40 良好 / 30–35 可接受）。

## 压缩损失占比很小
以 400px 为例，把"纯缩放基准"（原图降到 400 再比）和实际变体比：
| 图片 | 纯缩放基准 | 实际 webp | 差异 |
|---|---|---|---|
| kongming-architecture | 24.1 dB | 23.7 dB | 0.4 dB |
| xingju-cyberpunk | 25.9 dB | 25.0 dB | 0.9 dB |
| zen-workflow | 26.9 dB | 26.6 dB | 0.3 dB |

（该口径是"都放大回 1600"比的，用于**分离**缩放损失与压缩损失。）
差异只有 0.3–0.9 dB，说明**压得太重的部分几乎没有**，损失主要来自尺寸缩减本身。

## 编码参数
- 原图：1600×900, JPEG quality 85
- 现用 jpg：1200×675, quality **84**（与原始质量基本一致）
- WebP 变体：quality **92**

## 哪个设备取哪个变体（实测 srcset 选择）
`sizes="(max-width: 980px) 100vw, 720px"`

| 设备 | 选中变体 |
|---|---|
| 375/390/320 @1x | **400** |
| 390 @2x | 800 |
| 390 @3x | 1200 |
| 768 @1x / @2x | 800 / 1200 |
| 1280 @1x / @2x | 800 / 1200 |

即 **1x 手机取 400px、2x 手机取 800px**，没有"取了用不到的更大图"或"取小了"的情况。

## 复跑方式
```bash
# 同尺寸口径
for v in 400 800 1200; do
  convert 原图.jpg -resize <对应尺寸>! -quality 95 /tmp/ref.jpg
  compare -metric PSNR /tmp/ref.jpg 变体.webp null:
done
```

## 仍然需要人工确认的
以上都是**数值**证据。PSNR 35–38dB 在同类站点里属正常水平，
但"看起来是否可接受"只有人眼能判断，尤其是带文字的示意图（文字边缘对压缩更敏感）。

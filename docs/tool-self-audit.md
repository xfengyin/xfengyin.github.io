# 验证工具的自检（工具坏了不能长得像健康）

## 为什么要做这件事

第 18 轮发现**对比度检测工具本身在系统性误报**：它把"顶栏白字压在深青渐变上"
算成"白底白字 1.00:1"，而这个假阳性在报告里**连续出现了好几轮**，我一直口头带过没有深究。
教训：**一个坏掉却输出 ok 的检测器，比没有检测器更危险。**

所以要对每个工具做一次「故障注入」：故意植入它该发现的缺陷，看它报不报。
只测"正常时安静"是不够的——一个永远不响的报警器和没有报警器是一样的。

|---|---|---|

构建本身就是第一道闸，这是好事（多层防护）。

## 做故障注入时必须注意的两个坑（都踩过）

1. **注入会被构建覆盖。**
   我第一次测 `check-links.py` 时改了 `public/` 里的产物，然后跑脚本，
   而脚本前一步（或我上一条命令）跑了 `zola build`，产物被重新生成、注入消失，
   于是得到"没抓到"的**假阴性**，差点误判工具坏了。
   → 规矩：**注入必须发生在构建之后**，且注入后立刻确认文件里确实有那段内容。

2. **压缩后的 HTML 里没有 `</body>`。**
   我想用 `replace('</body>', ...)` 注入，但 Zola 开了 `minify_html`，
   HTML5 的 `</body>``</html>` 是可省略的，产物里根本不存在这个字符串，
   替换静默失败（`in` 检查才发现）。
   → 规矩：注入的锚点要选**确定存在**的东西（如文件末尾追加），并在注入后断言成功。

## 复跑方式

改动任何一个工具或模板后，建议按上面表格里的方式重新注入一遍验证。
（这些注入都是一次性的，测完必须还原 —— 本轮全部已还原，工作区已验证为 0 改动。）
